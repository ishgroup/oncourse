## 1. Summary

SST-260 is an **epic** for an AI chat assistant inside the onCourse staff UI ("Ask onCourse AI" floating button). Staff could use it to create courses, schedule classes, check clashes, look up records, get how-to guidance and (later) make changes. Every change is drafted on a review card and only applied after the user clicks Confirm `[Epic]`, `[Req doc]`.

The epic has 16 child stories (AI-01…AI-12 plus 4 stories added after comment `[C3]`), split into sprints:
- Sprint 5 "Foundations": spike, chat box, preferences/roles, permissions/audit, history.
- Sprint 6 "Read-only answers and guidance".
- Sprint 7 "Draft, confirm and undo".

**No AI/LLM code of any kind exists in the repo today** (client and server searched). The assistant would be new end to end. It could reuse a lot of existing server capability:
- REST API with per-role permission checks;
- session clash validation;
- a generic `x-validate-only` dry-run header;
- class duplicate/cancel/bulk-change endpoints;
- message recipient counting;
- the AQL compiler.

The main structural gaps are:
- no way to run API calls server-side "as the user" off the request thread;
- the audit log has no source flag, request text or before/after values;
- there is no public-holiday calendar or training.gov.au client;
- no endpoint does arbitrary aggregates for reporting questions;
- Groovy automations run with no sandbox.

The course-creation / scheduling / create-and-publish flow (requirements M-05…M-12), which is the headline of the epic, **has no child story yet**.

## 2. Requirements

### 2.1 Epic description (high-level) `[Epic]`

1. **E1 Entry point.** A floating "Ask onCourse AI" button on every dashboard page opens a chat panel with quick-action chips.
2. **E2 Course creation.** Draft a course from a unit code using training.gov.au data (name, qualification, duration, fee, web status) for review.
3. **E3 Scheduling.** Propose class dates, rooms, tutors and places. Work around double-bookings and public holidays.
4. **E4 Create and publish.** Create classes in bulk and publish them to the website once confirmed.
5. **E5 Beyond the mock:**
   - reschedule or cancel classes;
   - handle under-enrolment and waitlists;
   - look up students;
   - send reminders and messages;
   - answer reporting questions;
   - give how-to help;
   - undo actions.
6. **E6 Safeguards:**
   - confirmation before any change;
   - respect each user's onCourse permissions;
   - an audit log;
   - Australian privacy compliance;
   - WCAG 2.1 AA.
7. **E7 Limitations.** No payments or refunds, no deleting records, no issuing certificates or results, no government data submissions.

### 6.1 New assistant service (not in any existing module)

## 7. Open questions / ambiguities for the product owner

1. **Approved design.** The claude.ai artifact (the "Full requirements doc") is still unapproved and inaccessible `[C1]`, `[C2]`. Is the attached `.docx` the baseline to build against? Where is the Figma file referenced in the doc?
2. **Missing requirement IDs.** A-25…A-27 and L-16…L-22 are cited by SST-261…264 but absent from the attached doc. Please attach the revision that defines them, and the "delivery plan" with the standard DoD.
3. **Core flow has no stories.** M-05…M-13 (draft course, propose schedule, create and publish), plus A-01/A-02/A-07/A-13/A-14/A-21/A-23 (all Must), have no child story. Is that intentional for after the Pilot go/no-go, and which sprint?
4. **"Every dashboard page".** In onCourse, "Dashboard" is only `/`. Should the button appear on every logged-in staff screen (list views, edit views, preferences), and how should it coexist with the list `BottomAppBar` and Fab at bottom-right?
5. **Architecture and data residency (AI-01).** Which model/provider and AU region are acceptable? Server-side assistant in `angel` vs a separate service? Who pays per request? Per-college opt-in only? Is sending student PII to a model in an AU region compliant with N-04 as the business reads it?
6. **Public holidays and multi-state colleges.** M-09/N-09 derive holidays from the *Default server time zone*. Sites have their own time zones, and a time zone is not a state (e.g. Australia/Sydney covers NSW and ACT). Should holidays be per Site (state field?), and what source should be used (data.gov.au, a library, college-entered holidays)?
7. **training.gov.au.** No client exists in this repo, and the Module/Qualification sync mechanism isn't here. Is a live TGA web-service integration in scope (credentials, rate limits), or should the assistant only read existing Module/Qualification records? What "duration" and "fee" source does M-05 expect?
8. **Role setting semantics.** Should "Full / Read-only / None" be a new permission key using existing Hide/View/Edit levels? Should "Full" still be limited by the user's other permissions? (Yes per N-02, assumed.) Default for existing roles? Should Admins always get Full?
9. **Audit and undo.** Is it acceptable to add columns to `Audit` (source, request text, before/after)? Today updates log only field names. What does "Undo" (A-21) cover (the last assistant action only, or any time window), and how should it treat side effects already triggered (emails sent by automations, website updates)?
10. **Side-effect warnings accuracy.** Student notification on cancel depends on an optional automation (default not installed). Should the assistant check installed automations before saying "will notify N students"?
11. **Chat history scope.** "Survives moving between pages" vs "multiple browser tabs" (SST-275 DoD). Should tabs share one history (localStorage/server) or be independent (sessionStorage)? Should history persist across a full page reload? Should it be stored server-side at all (privacy)?
12. **Contradictions.**
    - A-12 "prompt certificate issue" vs L-04 "never issue certificates".
    - A-11/A-13 "draft reminders" vs L-11 "never sends messages itself" (draft-only is fine, but a draft entity doesn't exist).
    - SST-263 says users need the "Automations" permission, but onCourse has only "Scripts", with View always allowed.
13. **Automation safeguards.** "Second admin's approval before enabling" and "approved blocks only" are new workflow and model concepts. Should they apply to all script edits, or only assistant-made ones? Is SST-264's sandbox (allow-list, block reflection/IO) meant for all Groovy scripts? That would affect existing customer scripts.
14. **Sprint data.** All children carry sprint "Sprint 5" and status "Wishlist", while descriptions plan Sprints 5, 6 and 7 and the epic is "Ready". Which is authoritative?
